# 2026-08-04 元 Prompt 动态 Skill 与静态围栏的取舍

## 起因

今天讨论了一个趋势：通过元 Prompt（Meta-Prompting）动态生成或接入 Skill，而不是把 Skill 固定写成一组静态脚本、OpenAPI schema 或插件代码。

这个思路的关键吸引力在于：AI 模型越强，同一个 Prompt 生成出来的 Skill 可能越好；如果本地服务、CLI 或 API 文档发生变化，Agent 可以在运行时读取最新文档并自适应，而不是等待人工维护静态代码。

这对 AI Agent 生态很重要。它把 Skill 从“固定代码资产”推向了“声明式意图 + 运行时能力发现 + 当前模型自适应执行”。

## 直觉判断

这个方向是对的，但不能简单替代当前仓库的围栏模型。

原因是：动态生成适合处理“能力变化”，不适合承担“安全不变量”。

也就是说：

```text
外部接口会变 → 适合动态发现
安全边界不能变 → 必须代码强制
```

如果把 SQL 只读、SSH 命令白名单、Git 保护分支、凭据脱敏、写入确认这些东西交给 Prompt 动态生成，就会把确定性安全边界重新变成模型自觉。这和本仓库一直坚持的“代码围栏替代提示词祈祷”是冲突的。

## 静态 Skill 与动态 Skill 的差异

| 维度 | 静态写死的 Skill | Prompt 驱动动态 Skill |
|---|---|---|
| 确定性 | 高，行为可审计 | 依赖模型理解和当前上下文 |
| 维护成本 | 接口变化时需要更新 | 可通过最新文档动态适配 |
| 安全边界 | 适合代码强制 | 不适合作为唯一边界 |
| 演进能力 | 依赖人工迭代 | 随模型能力增强而变强 |
| Token 成本 | 低 | 需要读取文档、推理、生成方案 |
| 适合场景 | 高风险操作、围栏、审计 | 易变 API、CLI、MCP、模板、工作流适配 |

## 推荐架构：静态围栏 + 动态能力发现

后续 Skill 的推荐设计不是二选一，而是混合：

```text
静态 Skill
  ├─ 代码围栏：不可绕过的安全边界
  ├─ 动态发现：运行时读取 CLI help / schema / OpenAPI / Markdown 文档
  ├─ 元 Prompt：让当前模型在围栏内生成临时执行策略
  └─ 经验沉淀：把稳定经验写回 references / wrapper / tests
```

核心原则：

1. **不变的规则写死**：只读、白名单、危险命令拦截、凭据脱敏、审计、确认门槛。
2. **变化的接口动态发现**：CLI 参数、API schema、scope、MCP 工具可用性、构建工具行为。
3. **AI 只在围栏内自适应**：动态发现不能放宽安全限制。
4. **成功经验要沉淀**：本轮动态探索证明可复用后，补到 `references/`、wrapper 或测试。
5. **动态规则一旦变成必须遵守，就代码化**：不能长期停留在提示词提醒层。

## 对当前仓库的影响

### 适合优先优化的 Skill

| Skill | 优化方向 |
|---|---|
| `lark-cli-config` | Feishu/Lark CLI、scope、schema、OpenAPI 变化快，适合执行前动态读取 `--help`、`schema` 和官方文档 |
| `skill-dev` | 作为元 Skill，需要把“何时动态发现、何时代码围栏”写进开发规范 |
| `web-demo-publisher` | Vite、Slidev、cpolar、模板生态变化快，适合动态探测当前项目和工具能力 |
| `work-orchestrator` | 本来就是能力路由器，可加强运行时 Skill/MCP 可用性探测 |

### 不应动态化核心围栏的 Skill

| Skill | 原因 |
|---|---|
| `postgres-query` | SQL 只读、危险关键字、行数/超时上限必须代码强制 |
| `server-docker-logs-readonly` | 服务器命令、路径、SSH/Docker 权限必须白名单脚本控制 |
| `git-trunk-workflow` | 本地 Git 写操作、保护分支、worktree 隔离不能由模型临时决定 |
| `ai-delivery-hook` | hook 校验、active session、prepared hash 必须确定执行 |

## 本次落地的小改

本次不做大规模动态 Skill 生成器，只做方案 A 的最小沉淀：

1. 在 `skill-dev` 设计规范中新增“静态围栏 + 动态能力发现”。
2. 在 `skill-dev` 的核心判断中补充：外部接口易变时保留动态发现入口，不写死 API/CLI 参数细节。
3. 在 `lark-cli-config` 中强化“不支持功能时”的动态发现规则：优先只读探测最新 CLI/schema/docs，临时方案必须区别于稳定 wrapper，高风险操作仍回到 preflight/确认流程。
4. 用本文档记录本次判断，作为后续设计取舍依据。

## 后续可探索方向

后续可以考虑新增一个实验性 Skill，用来验证真正的动态接入范式：

```text
输入：本地服务 Markdown API 文档 / OpenAPI / CLI help
输出：本轮临时 adapter 使用计划 + 可选 wrapper 草案 + 安全风险分级
```

但它应该先定位为“能力发现器”或“wrapper 草案生成器”，而不是直接替代现有高风险执行层。

判断标准仍然是：

```text
能错一次也可恢复的，交给动态 Prompt。
错一次就可能造成数据丢失、凭据泄露、线上事故的，必须代码围栏。
```

## 最终结论

元 Prompt 动态 Skill 是 Agent 架构演进的重要趋势，尤其适合解决接口适配和能力持续进化问题。

但对当前仓库来说，最稳的路线是：

> **代码围栏不动，外部接口动态发现，AI 在围栏内自适应执行。**

这既保留了动态 Skill 随模型进化的优势，也不牺牲当前仓库最核心的安全资产：可审计、可测试、不可绕过的代码围栏。
